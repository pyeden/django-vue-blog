# 41. 总结

## 本章目标

- 回看这 43 章到底交付了什么。

- 把架构取舍讲清楚，方便你改成自己的站点。

## 原教程怎么做

原教程在最后列出已覆盖的功能：博文管理、用户、多级评论、栏目标签、图片、第三方登录、点赞、测试、部署和小功能，然后建议继续学响应式、类视图库、Haystack 搜索和 Linux 运维。

## 本实作怎么做

本实作按同一功能路线重做，但技术栈换成了 Django 4.2 + DRF + Vue 3。最终结构是四个 Django app 加一个 SPA：

- `accounts`：Profile、注册登录、资料、头像、密码重置、注销。
- `blog`：文章、栏目、标签、Markdown 渲染、目录、分页、搜索、最热、浏览量、点赞。
- `comments`：两级评论树、软删除、评论通知。
- `notices`：通知列表、未读数、单条与全部已读。
- `frontend/src`：首页、详情、写作、编辑、登录注册、资料、搜索、归档、通知、404。

已经实际验证过的：50 个后端测试全绿；前端 `npm run build` 成功（Vite 输出 `✓ built in 676ms`）；本地 API 的注册登录、发文改文删文、点赞、两级评论、通知、搜索、分页、最热、头像上传都有测试覆盖；生产脚本和 nginx 配置已写好，但公网验收还没过。

没有完成或没有启用的，也要列清楚：GitHub OAuth 未接入；文章上下篇快捷导航未实现；前端没有组件测试和端到端测试；nginx 子路径配置因 reload 需要管理员权限，公网仍是 404。把这些写出来，比在总结里假装“全部完成”有用。

架构上最重要的三个决定：用 `ArticleLike` 唯一约束做点赞幂等，而不是只改计数；用自关联 `parent` 加序列化递归做评论树，不引入 mptt；用一张自己的 `Notification` 表，不引入通知框架。它们都牺牲了一点“通用性”，换来更少的依赖和更清楚的代码。

## 在 MacBook 上操作

做一次最终验收：

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py test

cd ../frontend
npm run build
```

再跑接口冒烟：

```bash
cd ~/work/django-vue-blog
BASE=http://127.0.0.1:8000 bash qa/smoke_api.sh
```

冒烟脚本会注册登录、发文、改文、点赞两次、评论、删除、搜索、通知，最后输出 `PASS=n FAIL=0`。它需要本地后端和 `demo/demo12345` 账号，跑之前先 `seed_demo`。

## 踩坑与差异

最大的教训是“教程能跑”不等于“环境能跑”。原教程假设 Windows、根路径、可直连软件源；实际环境是 macOS、子路径、GitHub 被墙、系统 Python 版本不对。每换一个假设，部署就多一个坑。

第二个教训是依赖越少越好。mptt、通知框架、allauth 都能省事，但每一个都带来迁移、模板、配置和升级面。个人博客的功能边界清楚，自己写一张表反而更容易维护。

第三个教训是测试要测行为，不要测实现。点赞测试断言的是返回的 `liked/likes` 和数据库行数，不是“有没有调用某个函数”；这样以后重写 action，测试仍然有效。

## 小结

教程到这里结束，但项目还可以继续长。下一步我建议按这个顺序补：先拿到 nginx 权限完成上线验收，再加文章上下篇，然后补前端端到端测试，最后才考虑 GitHub 登录。不要反过来先加功能，否则线上问题会和功能问题混在一起。
