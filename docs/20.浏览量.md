# 20. 浏览量

## 本章目标

- 给 `Article` 增加 `total_views` 字段，理解为什么用 `PositiveIntegerField`。
- 在详情接口里自增浏览量，并用 `F()` 表达式避免并发丢计数。
- 让返回给前端的文章对象带着自增后的值，而不是旧值。
- 清楚这套统计的边界：它只适合个人博客，不做去重，也不抗高并发。

## 原教程怎么做

原教程在 `ArticlePost` 模型里加 `total_views = models.PositiveIntegerField(default=0)`，做一次迁移，然后在文章详情视图里执行 `article.total_views += 1` 和 `article.save(update_fields=['total_views'])`。它还会提醒：更新时只写这一个字段，可以少写其他列，效率更高。统计逻辑就放在视图函数里，打开详情页就加一。

## 本实作怎么做

字段定义在 `backend/blog/models.py`：

```python
total_views = models.PositiveIntegerField(default=0)
```

`PositiveIntegerField` 在数据库层限制了不能存负数，比普通 `IntegerField` 更贴近“浏览量”的语义。详情自增在 `backend/blog/views.py` 的 `ArticleViewSet.retrieve`：

```python
def retrieve(self, request, *args, **kwargs):
    instance = self.get_object()
    Article.objects.filter(pk=instance.pk).update(total_views=F("total_views") + 1)
    instance.total_views += 1
    serializer = self.get_serializer(instance)
    return Response(serializer.data)
```

这里没有用 `instance.save()`，而是让数据库执行 `total_views = total_views + 1`。原因是两个请求同时读到 100，各自加一写回 101，会丢一次浏览；`F()` 把加法交给数据库，行锁保证最终是 102。更新之后还要手动 `instance.total_views += 1`，因为内存里的对象不会自动知道数据库变了；不补这一行，序列化器返回的还是旧值，前端会看到“刷新一次没变化”。

列表接口不会自增，只有 `GET /api/articles/{slug}/` 会。`ArticleSerializer` 把 `total_views` 设为只读，写文章时不能伪造浏览量。

前端 `frontend/src/views/ArticleDetailView.vue` 用 `fetchArticle(slug)` 取详情，页头直接显示 `article.total_views`。文章卡片 `ArticleCard.vue` 也显示“N 次浏览”，数据来自列表项里的同名字段。

## 在 MacBook 上操作

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
```

连续请求同一篇文章两次：

```bash
curl -s http://127.0.0.1:8000/api/articles/你的-slug/ | python3 -m json.tool | grep total_views
curl -s http://127.0.0.1:8000/api/articles/你的-slug/ | python3 -m json.tool | grep total_views
```

两次结果的 `total_views` 应相差 1。也可以直接刷新前端详情页，页头的浏览数会变化。

## 验证

- 数据库迁移后 `python manage.py makemigrations --check` 不应再提示缺少迁移。
- 详情请求两次，`total_views` 递增两次；列表请求不会让它增加。
- 用一个不存在的 slug 请求，应返回 404，且不会凭空创建记录。
- 删除文章后对应计数随记录一起消失，不需要额外清理。

## 踩坑与差异

- 原教程用“读出来加一再保存”，单机低并发够用；这里换成 `F()`，是为了不在教程里留下一个明显的并发漏洞。
- 当前每次详情请求都加一，包括作者自己、爬虫、刷新页面。要做“同一会话只算一次”，需要额外存 Redis 或浏览记录表，本项目没有做。
- `instance.total_views += 1` 不能省；这是“数据库已更新、响应仍旧值”的经典坑。
- 如果之后给 Article 加了缓存，自增后要记得失效详情缓存，否则数字会停住。
- 浏览量没有和 `ArticleLike` 联动，点赞不会增加浏览数，两者是独立指标。

浏览量只是展示指标，不能拿来判断文章质量，也不该影响作者的操作权限。它和点赞、评论数一起出现在卡片上，读者可以快速判断一篇旧文是否值得点开。当前所有统计都直接落在 SQLite 的同一行上，写多读少时没问题；如果以后加缓存或读写分离，必须重新考虑自增的落点。
