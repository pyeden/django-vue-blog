# 36. 测试

## 本章目标

- 用 Django `TestCase` 覆盖文章、评论、通知、账号四条主线。
- 让权限、幂等、树形结构这些容易回归的点有自动化断言。
- 跑出一份可复现的结果，而不是只靠手点页面。
- 知道哪些行为测试没有覆盖。

## 原教程怎么做

原教程从“给文章模型写一个有 bug 的 `was_created_recently()`”开始，先手写测试暴露 bug，再讲 `TestCase`、`setUp`、断言和 `python manage.py test`。示例集中在文章模型和视图，规模较小。

## 本实作怎么做

测试按 app 分开，全部放在各自的 `tests.py`：

- `backend/blog/tests.py`：23 个，文章 CRUD、slug、分页、搜索、栏目标签过滤、排序、详情、Markdown 与 XSS、点赞、最热、栏目标签接口、404。
- `backend/comments/tests.py`：9 个，中文 slug、匿名拒绝、通知、两级树、跨文章父评论、删除权限。
- `backend/notices/tests.py`：6 个，登录要求、列表形状、归属隔离、单条已读、全部已读。
- `backend/accounts/tests.py`：12 个，Profile 信号、注册、登录退出、CSRF、资料、头像、重置密码。

接口测试统一用 `rest_framework.test.APIClient`。需要登录时用 `force_authenticate(user=...)` 绕过 session，专注权限逻辑；需要验证 CSRF 时用真实客户端请求 `/api/auth/csrf/`，断言 cookie 存在。图片上传统一用 1×1 的 PNG 字节，避免依赖测试机上的图片文件。

每个测试类在 `setUp` 里建自己的用户和文章，测试之间不共享数据库状态。比如文章测试固定建 `author`、`other`、`staff` 三个账号，权限用例直接切换身份；评论测试固定建作者、评论者和路人，避免每条测试重复写登录代码。这样单个测试可以独立跑，顺序打乱也不互相污染。

关键断言举两个。点赞幂等：

```python
first = self.client.post(f"/api/articles/{article.slug}/like/")
self.assertEqual(first.json(), {"liked": True, "likes": 1})
second = self.client.post(f"/api/articles/{article.slug}/like/")
self.assertEqual(second.json(), {"liked": False, "likes": 0})
```

评论树归并：

```python
deep = self.post_comment("回复的回复", parent_id=reply["id"])
self.assertEqual(deep.json()["parent_id"], root["id"])
```

这些断言直接对应 `SPEC.md` 的验收标准，不是为覆盖率凑数。文章测试还专门验证了列表项的字段集合，防止某次改序列化器时悄悄少掉 `excerpt` 或 `comment_count`，前端直到运行时才发现。

分页测试也不是只看状态码：八篇文章默认返回六条，`page_size=3&page=2` 返回三条且 `previous` 非空。这类断言比“200 就算过”更能挡住回归。

## 在 MacBook 上操作

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python -V
python manage.py test
```

实际 Python 版本是 3.12.2。全量测试的实际输出末尾：

```text
Ran 50 tests in 14.764s

OK
Destroying test database for alias 'default'...
```

中间会出现若干 `WARNING django.request: Forbidden` 和 `Unauthorized`，那是测试故意触发的 401/403，不是失败。测试库是临时创建的，结束后自动销毁。

也可以按 app 跑，输出更短：

```bash
python manage.py test comments   # Ran 9 tests in 3.340s, OK
python manage.py test notices    # Ran 6 tests in 1.680s, OK
python manage.py test accounts   # Ran 12 tests in 1.081s, OK
python manage.py test blog       # Ran 23 tests in 8.302s, OK
```

## 验证

“全绿”不够，至少抽查三条：

1. 把 `blog/views.py` 的点赞 `get_or_create` 改成无条件 `create`，`test_like_toggle_is_idempotent` 应失败。
2. 把评论视图里的父评论归并逻辑删掉，`test_reply_to_reply_is_normalized_to_root` 应失败。
3. 把 `ArticleViewSet` 的 `IsAuthorOrStaff` 去掉，`test_non_author_cannot_update_or_delete` 应失败。

每次改完记得还原。测试的价值在于它能红；永远绿的测试通常也永远没在测东西。

## 踩坑与差异

第一个坑是测试用的媒体文件。封面上传会写进 `MEDIA_ROOT`，测试结束后文件可能残留。当前用 1×1 PNG，体积可以忽略；要彻底清理，可以覆写 `tearDown` 或把 `MEDIA_ROOT` 指到临时目录。

第二个坑是 `force_authenticate` 会绕过 CSRF。它适合测权限，不适合测“没有 CSRF token 会被拒绝”。后者需要单独用 `Client(enforce_csrf_checks=True)`，本项目目前只在 cookie 层面验证，没有做完整的 CSRF 拒绝测试。

第三个差异是数据库。SQLite 跑测试很快，但并发和约束行为与 PostgreSQL 不完全一致。`ArticleLike` 的唯一约束测试在 SQLite 上通过，换库后仍应保留这条测试。

第四个缺口是前端。50 个测试全是后端 API，没有 Vue 组件测试，也没有浏览器端到端测试。页面交互仍靠 `qa/smoke_api.sh` 和手工检查。

## 小结

测试把后端行为钉住了，但线上出问题时还需要另一双眼睛：日志。下一章配置 `LOGGING` 和文件轮转。
