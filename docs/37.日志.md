# 37. 日志

## 本章目标

- 把 Django 的运行信息同时写到控制台和文件。
- 用轮转避免日志无限增长。
- 让 4xx/5xx 请求在线上有迹可循。
- 分清应用日志、gunicorn 日志和 launchd 日志。

## 原教程怎么做

原教程先讲 Logger、Handler、Filter、Formatter 四层，再给一个最小的 `LOGGING` 字典：把 `django` logger 的 DEBUG 消息写进 `logs/debug.log`。重点在概念，没有处理文件大小和轮转。

## 本实作怎么做

配置在 `backend/config/settings.py`，先确保目录存在：

```python
LOG_DIR = BASE_DIR / "logs"
LOG_DIR.mkdir(parents=True, exist_ok=True)
```

然后在 `LOGGING` 里定义两个 formatter：`verbose` 带时间、级别、logger 名，`simple` 只有级别和消息。两个 handler：

```python
"file": {
    "class": "logging.handlers.RotatingFileHandler",
    "filename": str(LOG_DIR / "app.log"),
    "maxBytes": 5 * 1024 * 1024,
    "backupCount": 3,
    "formatter": "verbose",
    "encoding": "utf-8",
}
```

也就是单文件 5 MB，最多保留三个备份，写满后自动改名为 `app.log.1`、`app.log.2`。个人博客的日志量不大，这个上限足够，也不会把磁盘吃满。

`root` 同时挂 `console` 和 `file`，默认级别从 `DJANGO_LOG_LEVEL` 读，缺省 `INFO`。`django` logger 单独配置并设 `propagate=False`，避免同一条消息被 root 再写一遍。`django.request` 固定 `WARNING`，所以 400、403、404、500 都会留下记录。正常请求不会写进 `django.request`，避免日志被 200 淹没；访问量看 gunicorn 的 access log 更合适。

根 logger 的级别可以由环境变量调整，生产缺省是 `INFO`。如果临时排查，把 `DJANGO_LOG_LEVEL=DEBUG` 写进 `~/djangovueblog-data/env` 再重启 launchd 服务；排查完改回 `INFO`，否则 SQL 和第三方库的调试信息会迅速把 5 MB 填满。

`accounts/views.py` 里已经有 `logger = logging.getLogger(__name__)`，目前主要靠框架的请求日志，业务里还没有大量 `logger.info()`。这是有意留的口子：需要排查注册或重置密码时，直接在这个 logger 上加一行即可，不用再改配置。

生产环境还有三层日志，不要混在一起：

- 应用轮转日志：`backend/logs/app.log`，随 release 目录走。
- gunicorn：`deploy/run.sh` 把 access 写到 `~/djangovueblog-data/logs/access.log`，error 写到同目录的 `error.log`。
- launchd：`com.seres.djangovueblog.plist` 的 `StandardOutPath` 和 `StandardErrorPath` 指向 `launchd.out.log`、`launchd.err.log`。

## 在 MacBook 上操作

启动开发服务器，随便访问一个不存在的地址：

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
curl -s -o /dev/null http://127.0.0.1:8000/api/articles/nope/
tail -n 8 logs/app.log
```

`app.log` 里的记录格式如下。下面这条来自测试请求，时间戳和路径会随操作变化：

```text
[2026-11-09 12:29:06,579] WARNING django.request: Not Found: /api/articles/nope/
```

格式来自 `verbose` formatter，不是 Django 默认样式。

## 验证

- 访问一个 403 接口，`app.log` 应新增一条 `Forbidden`。
- 把 `DJANGO_LOG_LEVEL=DEBUG` 后重启，SQL 查询等调试信息会增多；不要在生产长期开 DEBUG。
- 连续写入直到文件超过 5 MB，目录里应出现 `app.log.1`，原 `app.log` 重新从零开始。这个轮转由标准库完成，不需要额外脚本。
- 跑测试时控制台会打印大量 `WARNING django.request`，那是测试故意触发的 401/403，同时也会写进 `app.log`，属于预期。不要看到 WARNING 就以为测试失败，最终以 `OK` 和退出码为准。
- 生产上 `curl https://seres-ai.com/djangovueblog/api/health/` 如果返回非 200，先看 `launchd.err.log`，再看 `error.log`，最后才看 `app.log`。顺序反了会在无关日志里绕很久。

## 踩坑与差异

第一个坑是目录权限。`LOG_DIR.mkdir()` 在 import settings 时就执行，如果进程用户没有写权限，Django 起不来。生产 release 目录要保证运行 gunicorn 的用户可写 `logs/`。

第二个坑是相对路径。`filename` 用绝对路径，不用 `"logs/app.log"`。gunicorn 的 `WorkingDirectory` 变了以后，相对路径会写到意想不到的地方。

第三个差异是轮转边界。`RotatingFileHandler` 按大小轮转，不按天。想看“每天一个文件”要换 `TimedRotatingFileHandler`；本实作不需要，按大小更容易控制总量。

第四个坑是重复记录。`django` logger 设了 `propagate=False`，如果忘了设，root 也会处理一次，日志里会出现两条一样的记录。排查日志时先看有没有重复，再怀疑代码。

## 小结

日志让线上问题可回看，测试让问题可复现。下一章处理展示层的“格式化”，也就是原教程的模板过滤器和标签。
