# 22. 搜索

## 本章目标

- 理解博客搜索为什么用 GET：结果可收藏、可分享，刷新不会重复提交。
- 用 DRF 的 `SearchFilter` 在 `title` 和 `body` 上做包含匹配，不自己拼 SQL。
- 把关键词放进路由 query，让搜索页复用文章列表组件。
- 知道当前搜索没有关键词高亮、没有相关度排序，也没有全文索引。

## 原教程怎么做

原教程先比较 GET 和 POST，说明搜索应该用 GET，然后引入 Django 的 `Q` 对象，用 `Q(title__icontains=keyword) | Q(body__icontains=keyword)` 组合“标题或正文包含关键词”的条件。视图读 `request.GET.get('search')`，过滤后把结果和关键词一起传给模板。模板里再判断有没有结果，并显示“共找到 N 篇”。

## 本实作怎么做

搜索能力挂在 `ArticleViewSet` 上，配置在 `backend/blog/views.py`：

```python
search_fields = ["title", "body"]
```

`backend/config/settings.py` 的 `DEFAULT_FILTER_BACKENDS` 已经启用：

```python
"rest_framework.filters.SearchFilter",
"rest_framework.filters.OrderingFilter",
```

所以请求 `GET /api/articles/?search=django` 时，DRF 会自动生成 `icontains` 条件，等价于在标题或正文里找子串。它不区分大小写，中文也按子串匹配，足够个人博客使用。

`Q` 对象仍然在用，但位置不同：`get_queryset()` 里用 `Q(column__slug=column)` 和 `Q(column__id=int(column))` 兼容栏目 slug 与数字 id，标签则用 `tags__name__in=[tag]` 再 `distinct()`。搜索本身交给 `SearchFilter`，栏目、标签过滤则手写 `Q`，两者可以叠加，例如 `?search=vue&column=tech`。

前端路由在 `frontend/src/router/index.js` 是 `/search`，页面 `frontend/src/views/SearchView.vue` 从 `route.query.q` 读关键词，传给 `ArticleFeed`：

```js
const q = computed(() => String(route.query.q || '').trim())
const filters = computed(() => (q.value ? { search: q.value } : {}))
```

`ArticleFeed` 监听 `filterKey`，条件一变就回到第一页重新请求。侧栏搜索框和搜索结果页共用同一个接口，不需要两套逻辑。

## 在 MacBook 上操作

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
```

```bash
curl -s 'http://127.0.0.1:8000/api/articles/?search=django' | python3 -m json.tool | head -40
```

返回体是分页对象，`count` 是命中总数，`results` 是当前页。前端打开 `http://127.0.0.1:5173/search?q=django`，标题应显示“搜索：django”，列表只保留命中的文章。

## 验证

- `.venv/bin/python manage.py test blog.tests.ArticleApiTests.test_search_filter`：造两篇文章，只有标题含关键词的那篇应命中。
- 搜正文里的词也应命中，因为 `search_fields` 包含 `body`。
- 搜一个不存在的词，返回 `count=0` 和空 `results`，页面显示“没有找到匹配的文章”。
- 搜索加栏目过滤，例如 `?search=vue&column=tech`，结果应同时满足两个条件。

## 踩坑与差异

- 原教程在视图里显式写 `Q`；这里用 `SearchFilter`，条件是声明式的，换字段只改 `search_fields`。
- `SearchFilter` 默认用 `icontains`，在 SQLite 上就是 `LIKE '%词%'`，数据量大时会全表扫描。当前没有全文索引，也没有分页之外的性能优化。
- README 里写了“高亮”，实际前端没有做关键词高亮，只显示普通摘要；这是文档和实现的差距，我在这里纠正。
- 搜索没有相关度排序，命中顺序仍按 `-created`。标题命中不会排在正文命中前面，读者可能觉得“不够聪明”。
- 关键词为空时 `SearchView` 不发 `search` 参数，避免后端把空字符串当成条件。

搜索框放在侧栏而不是顶栏，是为了让关键词和列表在同一屏里，改词后立刻看到结果。输入被直接当成文本交给 ORM，参数化查询会处理转义，不需要手动拼 SQL。真正要补的是体验：空结果时给一句人话、保留用户输入的关键词，并让浏览器后退能回到上一次搜索结果，这些目前都由路由 query 自然满足。搜索结果也复用了分页，所以命中很多时不会一次画完。
