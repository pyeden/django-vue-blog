# 39. 点赞

## 本章目标

- 用一张关联表记录“谁赞了哪篇”，而不是只加数字。
- 用数据库唯一约束保证同一用户不能重复赞。
- 点赞和取消点赞都走一个幂等接口。
- 前端按钮根据服务端返回更新，不靠本地猜。

## 原教程怎么做

原教程不要求登录，点赞数存在 `ArticlePost.likes`，是否点过赞存在浏览器 `localStorage`。前端先查本地记录，没点过才发请求让后端 `likes += 1`。优点是游客也能点，缺点是换浏览器就能重复点，数据也不可审计。

## 本实作怎么做

本实作把判断放到服务端，模型在 `backend/blog/models.py`：

```python
class ArticleLike(models.Model):
    article = models.ForeignKey(Article, on_delete=models.CASCADE, related_name="article_likes")
    user = models.ForeignKey(User, on_delete=models.CASCADE, related_name="article_likes")
    created = models.DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["article", "user"], name="unique_article_like")
        ]
```

`unique(article, user)` 是硬约束。就算前端重复发请求，数据库也不会出现两条相同的点赞记录。

接口是 `POST /api/articles/<slug>/like/`，只允许登录用户。逻辑在 `ArticleViewSet.like`：

```python
like, created = ArticleLike.objects.get_or_create(article=article, user=request.user)
if created:
    Article.objects.filter(pk=article.pk).update(likes=F("likes") + 1)
    liked = True
else:
    like.delete()
    Article.objects.filter(pk=article.pk, likes__gt=0).update(likes=F("likes") - 1)
    liked = False
```

同一个接口承担点赞和取消：第一次创建记录并加一，第二次删除记录并减一。返回 `{liked, likes}`，前端不需要知道当前状态，照返回值渲染即可。

`F("likes")` 让加减在数据库里完成，避免“读出来加一再写回去”的并发覆盖。取消时的 `likes__gt=0` 是保险，防止历史脏数据把计数减成负数。更新后 `refresh_from_db(fields=["likes"])` 再返回，保证响应里的数字是数据库当前值。

前端在 `ArticleDetailView.vue`：

```js
const data = await toggleArticleLike(slug.value)
article.value.liked = data.liked
article.value.likes = data.likes
```

按钮的图标根据 `article.liked` 切换 `bi-heart` 和 `bi-heart-fill`，`liking` 为真时禁用，避免连点。未登录点击会跳到登录页，并带上 `redirect` 参数。

## 验证

手工验证要登录，且用两个账号：

1. A 账号点一次赞，按钮变实心，数字加一。
2. 再点一次，按钮变空心，数字减一。
3. B 账号点一次，数字再加一；A 的实心状态不受影响，因为 `liked` 是按当前用户查的。
4. 直接对同一篇文章重复 POST，返回的 `liked` 会在 true/false 之间切换，数据库里 `ArticleLike` 始终只有一条。

## 踩坑与差异

第一个坑是计数器与关联表可能不一致。比如手工删了 `ArticleLike` 行但没减 `likes`。本实作没有定时对账任务；真出问题时，可以用 `ArticleLike.objects.filter(article=a).count()` 重算并回写。日常操作都走同一个 action，正常不会漂。

第二个坑是并发。`get_or_create` 内部会捕获唯一约束冲突并重新查询，所以通常不会直接抛 `IntegrityError`；但在两个请求同时到达时，第二个请求可能拿到 `created=False`，于是走进“取消点赞”分支，把第一个请求刚建的行删掉。表现是计数来回跳，不是报错。当前按钮有 `liking` 锁，单用户连点不会触发；多标签页同时点仍有可能。要彻底稳，可以改成先查询再明确判断，或用 `select_for_update` 包住，这是可选加固，当前未实现。

第三个差异是登录要求。原教程为了降低门槛允许游客点赞；本实作要求登录，换来可审计和真正的幂等。对个人博客，这个取舍更符合“点赞是轻量认同，不是刷数据”。

第四个坑是列表页的 `likes` 与详情页不同步。列表接口返回计数，详情接口还返回 `liked`；从列表进详情会重新请求，所以不会拿旧状态。如果以后做局部刷新，记得两个字段一起更新。

## 小结

点赞把“唯一约束”用在了业务上，不只用来防脏数据。下一章是整套教程最重的一步：把项目真正部署到 Mac mini，并挂到现有域名的子路径下。
