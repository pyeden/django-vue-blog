# 43. 常见问题

## 本章目标

- 回答实作里反复出现的五个问题。
- 每个答案都指到具体文件和可执行命令。
- 分清“本地开发”和“生产子路径”的差异。
- 不把猜测写成结论。

## 原教程怎么做

原教程的 FAQ 集中在模板命名空间、Markdown 代码高亮、Popper.js 下载、邮件重置密码和前后端分离建议。大多是 Django 模板时代的问题，和本实作的 SPA 结构不完全对应。

## 本实作怎么做

**中文标题的 slug 怎么处理？** `Article.save()` 里用 `slugify(self.title, allow_unicode=True)`，保留中文，再截到 200 字符；如果重复，`_unique_slug()` 会追加 `-2`、`-3`。DRF 的 `lookup_value_regex = r"[^/.]+"` 允许非 ASCII 字符，所以 `/api/articles/中文标题/` 能匹配。前端请求用 `encodeURIComponent(slug)`，评论测试里用 `urllib.parse.quote()` 构造路径，都是同一个原因：中文要编码后再进 URL。

**登录后 CSRF 为什么会失效？** Django 在 `login()` 时会轮换 CSRF token。登录前拿到的旧 token 不能继续用。前端 `auth.login()` 先 `ensureCsrf()`，登录成功后 axios 拦截器每次写请求都重新从 `csrftoken` cookie 读取，所以不需要手动保存。`qa/smoke_api.sh` 在登录后也重新请求一次 `/api/auth/csrf/`，否则后面的发文会 403。生产还要保证 `CSRF_TRUSTED_ORIGINS=https://seres-ai.com`，并且 `DEBUG=False` 时 cookie 带 `Secure`。

**pip 一直卡在代理怎么办？** Mac mini 上的系统代理可能指向失效端口。`remote_install.sh` 在安装前执行 `export no_proxy='*'`，并把 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 清空，再走阿里云镜像。健康检查的 `curl` 也带 `--noproxy '*'`。如果手工装依赖，照这三行先清环境，不要一边报超时一边怀疑包版本。

**刷新前端路由为什么 404？** Vue Router 用 history 模式，`/djangovueblog/notifications` 在服务器上并不存在这个文件，必须由 nginx 回退到 `index.html`。配置里的 `try_files $uri $uri/ /djangovueblog/index.html;` 就是干这个的。前端 `base` 必须是 `/djangovueblog/`，否则 assets 路径也会错。当前公网仍是 404，原因是 nginx reload 没完成，不是回退规则写错。

**封面和头像的 URL 为什么有时是相对路径？** 序列化器用 `request.build_absolute_uri()` 返回绝对地址，正常生产是 `https://seres-ai.com/djangovueblog/media/...`。这依赖 nginx 传 `X-Forwarded-Proto` 和 `Host`，Django 侧靠 `SECURE_PROXY_SSL_HEADER` 与 `USE_X_FORWARDED_HOST` 还原。前端 `mediaUrl()` 遇到 `http(s)://` 原样返回，遇到相对路径才拼 `VITE_MEDIA_BASE`；本地开发返回 `/media/...`，由 Vite 代理接住。

## 在 MacBook 上操作

中文 slug 用测试验证：

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py test comments.tests.CommentApiTests.test_comment_on_chinese_slug_article
```

CSRF 用冒烟脚本验证，它会自动处理轮换：

```bash
cd ~/work/django-vue-blog
BASE=http://127.0.0.1:8000 bash qa/smoke_api.sh
```

pip 代理问题在生产机上按 `remote_install.sh` 的三行环境变量处理；本地一般不需要。

## 验证

- 中文 slug：详情、评论、点赞三个接口都能用编码后的路径访问，不出现 404。
- CSRF：登录后立刻发文应成功；如果手动复用登录前的 token，应得到 403。这说明轮换生效，不是 bug。
- pip：清代理后 `pip install` 不再长时间停在 `Retrying`。
- SPA：nginx reload 后直接访问 `/djangovueblog/notifications` 应返回 200 且内容是 `index.html`，不是 nginx 404 页。
- 媒体：封面和头像的 `src` 是完整 `https://` 地址，直接打开返回图片，不是 403 或 404。

## 踩坑与差异

第一个坑是把“本地能显示”当成“生产能显示”。本地 `/media/` 由 Django 或 Vite 代理，生产由 nginx alias，路径和权限都不同。上传成功不等于访问成功，必须用公网 URL 再开一次。

第二个坑是 `VITE_MEDIA_BASE`。生产环境它是空的，因为序列化器已经给绝对地址；如果随手填 `/djangovueblog/media`，相对路径会被拼两次，变成 `/djangovueblog/media/djangovueblog/media/...`。

第三个坑是 CSRF 与跨域。开发时前端 5173、后端 8000，靠 `CORS_ALLOWED_ORIGINS` 和 `CSRF_TRUSTED_ORIGINS`；生产同源，反而简单。不要把开发的宽配置原样带到生产。

第四个差异是 FAQ 的时代背景。原教程问 Popper.js 下载、模板 namespace；本实作对应的是 npm 依赖、Vue Router base 和 nginx 子路径。问题变了，排查方法还是一样：先确认请求到了哪一层，再看那一层的日志。

## 小结

这五个问题覆盖了实作里最容易卡住的地方：URL 编码、CSRF、代理、SPA 回退和媒体路径。先把它们排掉，再谈新功能。
