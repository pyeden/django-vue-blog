# 17. 用户资料

## 本章目标

- 用一对一模型扩展 Django 自带的 `User`，不重写用户系统，也不破坏 admin 和认证。
- 让每个新用户自动拥有 `Profile`，页面读取资料时不用到处判空。
- 提供 `GET/PATCH /api/profile/`，并在前端做资料编辑页。
- 理解为什么 `UserSerializer` 要把 profile 嵌进去，以及这样做对前端状态管理的影响。

## 原教程怎么做

原教程新建 `userprofile` app，写 `Profile` 模型，用 `OneToOneField` 指向 `User`，再用 `post_save` 信号在用户创建时自动建一条资料记录。模板里直接读 `user.profile.phone`、`user.profile.bio`，因为 Django 模板对空值比较宽容，判空逻辑写得不多。它没有单独的资料 API，资料随用户对象一起进模板上下文。

## 本实作怎么做

模型在 `backend/accounts/models.py`，没有再建一个 app：

```python
class Profile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE, related_name="profile")
    phone = models.CharField(max_length=32, blank=True, default="")
    bio = models.TextField(blank=True, default="")
    avatar = models.ImageField(upload_to="avatars/", blank=True, null=True)
```

选择一对一而不是自定义用户模型，是因为项目已经用了 Django 的 `User` 和 admin，重写 `AUTH_USER_MODEL` 要付出迁移和兼容成本。博客的资料字段只有电话、简介、头像，一对一足够，也不会影响 `authenticate` 和权限判断。

信号在 `backend/accounts/signals.py`：

```python
@receiver(post_save, sender=User)
def ensure_profile(sender, instance, created, **kwargs):
    Profile.objects.get_or_create(user=instance)
```

`backend/accounts/apps.py` 的 `ready()` 里导入 `signals`，否则接收器不会注册。这里用 `get_or_create` 而不是只在 `created` 时创建，是为了兼容 admin 新建用户、fixture 导入，以及很早就存在、没有经过信号的老用户。`ProfileSerializer` 把 avatar 做成 `SerializerMethodField`，有请求上下文时返回绝对 URL，前端不用自己拼域名。

接口在 `ProfileView`：GET 返回当前用户资料，PATCH 用 `ProfileSerializer(partial=True)` 更新 `phone`、`bio`。`UserSerializer` 通过 `get_profile` 把资料嵌进 `user.profile`，所以登录、注册、`/auth/me/` 返回的形状一致。前端只需要维护一个 `auth.user`，顶栏、评论头像和资料页都从它取值。

前端 `frontend/src/views/ProfileView.vue` 进页面先 `fetchProfile()`，保存时 `updateProfile({phone, bio})`，成功后 `auth.refresh()`，让顶栏头像和简介同步。左侧卡片显示头像或用户名首字，右侧是编辑表单，删除账号也放在这个页面。

## 在 MacBook 上操作

如果是第一次加这个模型：

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py makemigrations accounts
python manage.py migrate
```

检查已有用户是否都补上了资料：

```bash
python manage.py shell -c "from django.contrib.auth.models import User; print([(u.username, hasattr(u, 'profile')) for u in User.objects.all()])"
```

admin 里也能看到 `Profile`，`backend/accounts/admin.py` 注册了 `ProfileAdmin`，可以按用户名或电话搜索。

## 验证

- `.venv/bin/python manage.py test accounts.tests.ProfileSignalTests` 应全绿，覆盖普通用户、超级用户和“不重复创建”三种情况。
- 登录后 PATCH：

```bash
curl -i -X PATCH http://127.0.0.1:8000/api/profile/ \
  -H 'Content-Type: application/json' \
  -d '{"phone":"13800000000","bio":"写点东西"}'
```

需要带上会话 Cookie 和 CSRF 头；在浏览器里直接操作资料页更省事。
- 刷新个人资料页，电话和简介应保持；再刷新顶栏，用户名旁边的资料也应同步。
- 未登录 PATCH 应返回 401 或 403，不能匿名改资料。

## 踩坑与差异

- 忘记在 `apps.py` 导入信号，是最常见的“Profile 不自动创建”原因。表现是登录正常，但一读 `user.profile` 就报 `RelatedObjectDoesNotExist`。
- `related_name="profile"` 让模板和序列化器都能写 `user.profile`；如果用了默认名，代码会变难读。
- 原教程单独建 app；这里合并进 `accounts`，减少跨 app 依赖，也让 `UserSerializer` 不用跨包导入。
- 目前没有做资料字段的额外校验，电话只是字符串，长度上限 32；简介上限由前端 `maxlength=500` 控制，后端没有强制。
- `UserSerializer` 每次序列化都会 `get_or_create`，对老数据是兜底，但频繁调用会多一次查询；用户量大了应改成信号保证存在后直接读。
