# 33. 通知

## 本章目标

- 有人评论文章时，给作者留一条通知。
- 通知列表只返回最近二十条，并附带未读数。
- 支持单条已读和全部已读。
- 顶栏用小红点提醒，不打扰阅读。

## 原教程怎么做

原教程安装 `django-notifications-hq`，在评论保存后调用 `notify.send(actor, recipient, verb, target, action_object)`，再用它自带的 `inbox/notifications/` 路由和模板显示列表。好处是开箱即用，代价是多一个 app、多一套迁移和模板约定。

## 本实作怎么做

本实作只在 `backend/notices/models.py` 里定义了一张表：

```python
class Notification(models.Model):
    recipient = models.ForeignKey(User, on_delete=models.CASCADE, related_name="notifications")
    actor = models.ForeignKey(User, on_delete=models.SET_NULL, null=True, blank=True)
    verb = models.CharField(max_length=50)
    target_article = models.ForeignKey(Article, null=True, blank=True, on_delete=models.CASCADE)
    target_comment = models.ForeignKey("comments.Comment", null=True, blank=True, on_delete=models.CASCADE)
    unread = models.BooleanField(default=True)
    created = models.DateTimeField(auto_now_add=True)
```

字段是照 `SPEC.md` 的响应形状设计的，没有引入通用活动流。`actor` 用 `SET_NULL`，用户注销后通知还在，只是显示“有人”。

写通知的位置在 `comments/views.py` 的 `post` 里，评论创建之后：

```python
if article.author_id != request.user.id:
    Notification.objects.create(
        recipient=article.author,
        actor=request.user,
        verb="commented",
        target_article=article,
        target_comment=comment,
    )
```

自己评论自己的文章不通知，避免每次写完文章都被自己烦到。通知在 `comment` 保存之后创建，所以 `target_comment_id` 一定有值。

接口有三个：`GET /api/notifications/` 返回 `{unread_count, results}`，列表切片 `[:20]`；`POST /api/notifications/read-all/` 批量置为已读；`POST /api/notifications/<id>/read/` 只处理属于当前用户的通知，别人的通知返回 404，不泄露存在性。

注意 `unread_count` 统计的是全部未读，不只是最近二十条。列表只展示二十条，是为了让响应稳定；更早的通知仍算未读，但不会撑大页面。这个取舍在个人博客里够用，真要翻历史再加分页。

通知项的形状是 `{id, verb, actor, article, unread, created}`。`actor` 只返回用户名字符串，`article` 只返回标题和 slug，前端不需要再请求一次用户或文章详情。字段少，列表加载就快。

前端状态在 `frontend/src/stores/notifications.js`。`App.vue` 登录后每 60 秒刷新一次，并在 `visibilitychange` 回到前台时再拉一次；退出登录时 `reset()` 并清掉定时器。顶栏 `AppHeader.vue` 读 `unreadCount`，大于零才渲染带数字的 `.notif-dot`，超过 99 显示 `99+`。

`NotificationsView.vue` 把未读项加上 `.unread` 类，左侧小圆点由 CSS 控制；点击整行调用 `readOne`，先本地减一，再发请求。列表为空时用 `EmptyState` 提示“有人评论你的文章时，会出现在这里”。`readAll` 会把本地所有项标成已读并把计数清零，不需要等下一次轮询。

通知文案没有做模板化，固定成“某人评论了《标题》”。因为当前只有 `commented` 一种动词，多做一层动词映射反而增加维护面；以后加 `replied` 或 `liked` 时再抽成小函数。

## 在 MacBook 上操作

准备两个账号：作者 A 和评论者 B。用 B 登录，在 A 的文章下留言，然后切回 A：

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
```

前端照常 `npm run dev`。A 的顶栏铃铛应出现数字，点进 `/notifications` 能看到“B 评论了《标题》”。

## 踩坑与差异

原教程的 `notify` 依赖信号，容易在对象还没保存时拿到空 `action_object`。本实作把创建通知放在 `Comment.objects.create()` 之后，顺序是明确的，不需要猜信号触发时机。

第二个差异是通知范围。当前只有“文章作者收到评论通知”，回复某条评论时不会额外通知被回复的人；点赞也不发通知。这不是遗漏，而是先把最小闭环做稳。要扩展的话，在 `post` 里判断 `parent.user_id` 并再建一条 `verb="replied"` 即可。

第三个坑是轮询。60 秒一次对个人博客足够，页面隐藏时浏览器会节流定时器，所以补了 `visibilitychange`。如果以后要实时，可以换 SSE 或 WebSocket，但不建议为一个小站引入长连接运维成本。

第四个差异是数据清理。通知随文章级联删除，评论删除是软删除，通知不会跟着消失；点进去可能看到“评论已删除”的空列表。当前没有做清理任务，量大了可以加一条定期删除九十天前已读通知的命令。

## 小结

有了通知，读者知道去哪儿看回复。下一章解决“到了文章页，还要自己找那条评论”的问题。
