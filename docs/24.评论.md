# 24.评论

## 本章目标

- 设计 `Comment` 模型：文章、用户、正文、父评论、时间、是否可见。
- 用自关联 `parent` 表达回复关系，接口返回两层评论树。
- 实现“回复的回复归到根评论”，避免树无限深。
- 在详情页做评论列表、发表、回复、删除，并理解软删除。

## 原教程怎么做

原教程新建 `comments` app，写 `Comment` 模型，字段包括所属文章、评论用户、正文和创建时间，然后在文章详情页加评论表单和评论列表。视图接收 POST，保存后重定向回详情页。它先做单层评论，多级回复留到后面的章节，用 `django-mptt` 之类的树形方案处理。

## 本实作怎么做

模型在 `backend/comments/models.py`，没有引入 mptt：

```python
class Comment(models.Model):
    article = models.ForeignKey(Article, on_delete=models.CASCADE, related_name="comments")
    user = models.ForeignKey(User, on_delete=models.CASCADE, related_name="comments")
    body = models.TextField()
    parent = models.ForeignKey("self", on_delete=models.CASCADE, null=True, blank=True, related_name="replies")
    created = models.DateTimeField(auto_now_add=True)
    active = models.BooleanField(default=True)
```

`related_name="replies"` 让父评论能直接取子评论；`active` 用于软删除，删除时不真的删行，避免回复一起消失。`Meta.ordering = ["created"]` 保证同层按时间正序。

读取接口 `ArticleCommentsView.get` 只取 `parent__isnull=True` 且 `active=True` 的根评论，`select_related("user", "user__profile")` 减少用户查询，`prefetch_related("replies__user__profile")` 预取回复。`CommentSerializer.get_replies` 递归序列化子评论，所以一次请求就能拿到两层树。

发表接口 `post` 先校验登录和文章存在，再处理 `parent_id`。如果父评论不属于这篇文章，返回 400；如果父评论本身已经是回复，就把 `parent` 改成它的父级：

```python
if parent.parent_id is not None:
    parent = parent.parent
```

这样前端即使对一条回复再回复，数据库里仍然只有两层，渲染不会无限缩进。评论创建后，如果评论者不是作者，会写一条 `Notification`，`verb="commented"`，目标指向文章和评论。

删除接口 `CommentDetailView` 只允许作者或 staff，执行 `comment.active = False` 后返回 204。读取时过滤 `active=True`，所以评论立即消失，但数据还在。

前端 `CommentTree.vue` 渲染根列表，`CommentNode.vue` 递归渲染 `replies`，每层都能回复和删除。发表成功后触发 `changed` 事件，详情页重新拉取评论树，保证顺序和服务端一致。

## 在 MacBook 上操作

```bash
cd ~/work/django-vue-blog/backend

```

```bash
curl -s http://127.0.0.1:8000/api/articles/你的-slug/comments/ | python3 -m json.tool
```

未登录时这是只读接口，返回评论数组。发表评论需要会话 Cookie 和 CSRF，直接在浏览器详情页操作更简单：登录、输入正文、点“发表评论”，再对某条评论点“回复”。

## 验证

- `.venv/bin/python manage.py test comments.tests.CommentApiTests`：覆盖中文 slug、匿名拦截、通知、两级树、回复归并、跨文章父评论、删除权限。
- 发表一条根评论，接口返回 `parent_id=null`、`replies=[]`。
- 回复根评论，返回的 `parent_id` 是根评论 id；再回复这条回复，`parent_id` 仍是根评论 id。
- 删除根评论后，`GET` 列表里不再出现它，数据库行的 `active` 变成 `False`。

## 踩坑与差异

- 原教程用 mptt 管理树；这里用自关联加“归并到根”的规则，结构简单，代价是只支持两层。
- 删除是软删除。删掉根评论后，它的回复仍然 `active=True`，但因为根不可见，回复也读不到；这是有意的隐藏效果，不是数据丢失。
- `CommentSerializer` 递归没有深度限制，靠写入时的归并保证不会爆栈；如果绕过接口直接写数据库，仍可能造出深树。
- 评论没有编辑功能，也没有频率限制和敏感词过滤。公开站点上线前至少要加限流，否则很容易被刷。
- 通知创建和评论创建在同一个请求里，失败会一起回滚；这让逻辑简单，但也意味着通知表出问题会阻塞评论。
