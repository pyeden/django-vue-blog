# 32. 多级评论

## 本章目标

- 用自关联外键表达“评论的评论”。
- 让 API 直接返回嵌套树，而不是让前端自己拼。
- 用递归组件渲染任意层级的回复。
- 把树限制在两级，避免页面无限缩进。

## 原教程怎么做

原教程引入 `django-mptt`，把 `Comment` 改成 `MPTTModel`，用 `TreeForeignKey` 指向自己，模板里用 `{% recursetree comments %}` 递归输出。MPTT 会在表里维护左右值，查询子树很快，但模型和迁移都变复杂。

## 本实作怎么做

本实作没有引入 mptt，只加了一个普通自关联字段，位置在 `backend/comments/models.py`：

```python
parent = models.ForeignKey(
    "self", on_delete=models.CASCADE, null=True, blank=True, related_name="replies"
)
```

根评论的 `parent` 是 `None`。查询时先取根，再由序列化器递归取 `replies`：

```python
class CommentSerializer(serializers.ModelSerializer):
    replies = serializers.SerializerMethodField()

    def get_replies(self, obj):
        children = obj.replies.filter(active=True).select_related("user", "user__profile")
        return CommentSerializer(children, many=True, context=self.context).data
```

`comments/views.py` 的 `ArticleCommentsView.get` 只查 `parent__isnull=True` 的评论，并用 `prefetch_related("replies__user__profile")` 减少查询。返回形状是 `[{id, body, user, created, parent_id, replies: [...]}]`，与 `SPEC.md` 一致。`parent_id` 在序列化器里用 `source="parent.id"` 读出，前端只认这个整数，不需要再解析嵌套对象。

`POST` 接口要求登录，未登录直接返回 401。请求体只有 `body` 和可选的 `parent_id`，用户和文章都从 URL 与 session 里取，不接受前端伪造作者。

写入时做了两个约束：父评论必须属于同一篇文章且 `active=True`；如果回复的是一条回复，会把 `parent` 提升到它的根评论。这样数据库里最多两层，前端不会出现越缩越窄的“楼梯”。

删除不是物理删除，而是把 `active` 置为 `False`，列表查询会过滤掉。这样已有子评论不会因为父评论被删而一起消失。删除权限由 `IsCommentAuthorOrStaff` 控制：评论作者本人或 `is_staff` 可以删，其他人拿到 403。

`CommentDetailView` 只允许 `DELETE`，没有提供编辑评论的接口。个人博客里改评论的需求很少，先不做可以减少一类权限判断。

前端 `CommentNode.vue` 递归引用自己：

```vue
<CommentNode
  v-for="child in children"
  :key="child.id"
  :comment="child"
  :slug="slug"
  :depth="depth + 1"
  @changed="emit('changed')"
/>
```

组件里用 `defineOptions({ name: 'CommentNode' })` 声明名字，递归时才能解析到自己。回复表单直接调用 `createComment(slug, { body, parent_id })`，成功后 `emit('changed')`，由 `ArticleDetailView` 重新拉整棵树。数据量小，重拉比局部插入更不容易出错。

子评论容器 `.comment-children` 有左边框和 40px 缩进，视觉上把回复归到父评论下面。因为后端最多两层，这个缩进只会出现一次，手机上也不会把正文挤成一条缝。删除按钮只在 `canDelete` 为真时显示，判断依据是当前用户名等于评论用户名，或者当前用户是 staff。

## 在 MacBook 上操作

先确认后端在跑：

```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
```

前端另开一个终端：

```bash
cd ~/work/django-vue-blog/frontend
npm run dev
```

登录后在一篇文章下先发一条评论，再点“回复”发第二条。数据库里第二条的 `parent_id` 应指向第一条。再对第二条点一次“回复”，新评论的 `parent_id` 仍应指向第一条，而不是第二条，这是后端主动归并的结果。

也可以直接用 `curl` 检查返回树，但别忘了先取 CSRF token 并带上 session cookie；本项目的写接口都走 Session + CSRF，不是无状态的 JWT。

## 踩坑与差异

第一个坑是无限递归。序列化器如果不过滤 `active`，被软删除的评论还会出现在树里；如果父评论删除后子评论仍指向它，根查询又查不到，就会变成“孤儿”。本实作保留 `active` 过滤，孤儿不会显示。

第二个坑是 N+1。`CommentNode` 每层都访问 `user.profile.avatar`，不预取就会按评论数发查询。视图里的 `prefetch_related` 和序列化器的 `select_related` 要一起看。

第三个差异是层级。原教程的 mptt 支持任意深度；本实作主动压成两级。对个人博客来说，回复的回复继续挂到根评论更易读，也避免移动端缩进失控。如果以后要放开，去掉视图里的提升逻辑即可，模型本身支持更深，但序列化器也要防止递归过深。

第四个差异是查询方式。mptt 用左右值一次取子树；本实作按根评论逐层查，评论量大时会有更多查询。以个人博客的评论量，这个代价可以接受；真到几千条评论，再考虑加索引或换树方案。

## 小结

评论树搞定了，但作者怎么知道有人回复？下一章用一张轻量的通知表解决这个问题。
