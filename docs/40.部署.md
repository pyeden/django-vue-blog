# 40. 部署

## 本章目标

- 在 MacBook 构建，在 Mac mini 运行，不在部署机上装 Node。
- 在 Mac mini 上准备可用的 Python 3.12。
- 用 gunicorn + launchd 常驻后端。
- 用 nginx 子路径把站点挂到既有域名下。

## 原教程怎么做

原教程买一台阿里云 Ubuntu，装 nginx、Python、virtualenv，把代码上传后用 gunicorn 跑起来，再写 nginx 配置转发，最后用 supervisor 守进程。步骤完整，但假设服务器能直连软件源、站点占根路径。

## 本实作怎么做

本实作没有另买 VPS，而是把博客挂到已有的 `seres-ai.com` 下，路径是 `/djangovueblog/`。链路是：MacBook 构建前端 → rsync 到 Mac mini → Mac mini 上建 venv、迁移、收集静态 → launchd 拉起 gunicorn → nginx 按子路径转发。

**构建必须在 MacBook。** Mac mini 直连 GitHub 会超时，`brew update` 和 `brew install python@3.12` 都卡住；MacBook 能直连，所以 Node 构建、依赖准备都在 MacBook 完成。`deploy/release.sh` 做的事是：

```bash
VITE_BASE=/djangovueblog/ VITE_API_BASE=/djangovueblog/api npm run build
rsync -a --delete frontend/dist/ "$STAGE/frontend/djangovueblog/"
```

打包时排除 `.venv`、`db.sqlite3`、`__pycache__`、`logs`、`media`、`staticfiles`，再通过 `ssh codinglog-deploy` 把整个 release 目录 rsync 到 Mac mini 的 `~/djangovueblog-releases/<时间戳>-<sha>/`。

**Mac mini 的 Python 是单独解的。** 系统只有 Python 3.14，Homebrew 又被 GitHub 卡住。实际做法是下载 python.org 的 3.12.10 pkg，用 `pkgutil --expand-full` 解包，把 `Python.framework` 放到 `~/Library/Frameworks`，再用 `install_name_tool` 把框架里的绝对路径改成 `@executable_path` 相对路径，最后 `codesign -s -` 重新签名。这样不用安装器，也不会污染系统目录。`remote_install.sh` 里的解释器路径就是：

```bash
PY="$HOME/Library/Frameworks/Python.framework/Versions/3.12/bin/python3.12"
```

用它建 `~/djangovueblog-runtime/venv`，实测 `ssl` 和 `sqlite3` 都能导入。

**依赖安装强制直连。** macOS 的系统代理可能指向已经失效的端口，pip 会一直重试。脚本里先清空代理：

```bash
export no_proxy='*' NO_PROXY='*'
export HTTP_PROXY='' HTTPS_PROXY='' ALL_PROXY=''
"$RUNTIME/venv/bin/pip" install -i https://mirrors.aliyun.com/pypi/simple/ -r "$BASE/backend/requirements.txt"
```

第一次运行会生成 `~/djangovueblog-data/env`，写入 `DJANGO_DEBUG=False`、随机 `SECRET_KEY`、`ALLOWED_HOSTS`、`CSRF_TRUSTED_ORIGINS`、SQLite 路径、media 路径和 static 路径。每个 release 的静态目录不同，脚本用 `sed` 更新 `DJANGO_STATIC_ROOT`，然后 `migrate`、只执行一次的 `seed_demo`、`collectstatic`。

**gunicorn 由 launchd 守。** `run.sh` 先 `source` 环境文件，再：

```bash
exec .../gunicorn --bind 127.0.0.1:8899 --workers 3 --timeout 60 \
  --access-logfile .../access.log --error-logfile .../error.log config.wsgi:application
```

`com.seres.djangovueblog.plist` 设 `RunAtLoad` 和 `KeepAlive`，`remote_install.sh` 用 `launchctl bootstrap` 加 `kickstart -k` 重启。8899 是特意选的，避开机器上已有的 8080、8090、8092、23366、7788。

**nginx 只加一个 include。** 配置文件是 `deploy/nginx-djangovueblog.conf`，实际放到 `/Users/mac/coding-log-web/nginx/server/djangovueblog.conf`，由主配置 include。里面分五段：`/djangovueblog` 301 到带斜杠；`/djangovueblog/api/` 用 `proxy_pass http://127.0.0.1:8899/api/;` 去掉前缀；media `alias` 到数据目录；static `alias` 到 `current/staticfiles/`；SPA 用 `try_files $uri $uri/ /djangovueblog/index.html;` 回退。`assets` 单独加长缓存。

## 在 MacBook 上操作

```bash
cd ~/work/django-vue-blog
bash deploy/release.sh
```

脚本会构建、打包、上传并在 Mac mini 执行 `remote_install.sh`。构建前确认 `.env.production` 里 `VITE_BASE=/djangovueblog/`、`VITE_API_BASE=/djangovueblog/api`。

nginx 配置更新后需要 reload。**reload 需要管理员权限**，普通账号执行 `nginx -s reload` 会报权限不足；要用 `sudo nginx -s reload`，或让有权限的人通过服务器面板操作。这一步我没有权限直接完成，所以只把配置文件放好，没有假装已经生效。

## 验证

本地先过两道：

```bash
cd backend && source .venv/bin/activate && python manage.py test
cd ../frontend && npm run build
```

实际全量测试是 `Ran 50 tests in 14.764s`，结果 `OK`；前端构建成功。

远端先看脚本自带健康检查，它轮询 `http://127.0.0.1:8899/api/health/`，成功才退出。公网验证用：

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://seres-ai.com/djangovueblog/
curl -s -o /dev/null -w "%{http_code}\n" https://seres-ai.com/djangovueblog/api/health/
curl -s -o /dev/null -w "%{http_code}\n" https://seres-ai.com/djangovueblog/notifications
```

写这一章时实际请求前两条都返回 `404`，响应体还是原有的 VuePress 站点，说明子路径配置尚未生效，卡在 nginx reload 权限上，不是 Django 或 gunicorn 的问题。等 reload 完成后，三条都应返回 200，最后一条验证 SPA 刷新不 404。

## 踩坑与差异

第一个坑是 8888 端口的 PROXY protocol v2。直接 `curl 127.0.0.1:8888` 返回 `000`，必须经 frp 访问；验证要走公网域名，不要拿本机端口判断服务死活。gunicorn 的 8899 只监听回环，不对外。

第二个坑是权限。nginx worker 以 `nobody` 运行，release、`dist`、media 必须 `a+rX`。脚本最后执行 `chmod -R a+rX`，少这一步就是 403。

第三个坑是静态目录随 release 变。`DJANGO_STATIC_ROOT` 指向当前 release 的 `staticfiles`，nginx 却指向 `current/staticfiles` 符号链接；两者必须同步，否则页面加载的是上一版 CSS。

第四个坑是子路径。前端 `base`、API base、nginx location、Django 的 `STATIC_URL`/`MEDIA_URL` 四处都要带 `/djangovueblog/`。只改一处，表现是白屏、404 或静态资源 403。

第五个坑是 secrets。`SECRET_KEY` 只存在 `~/djangovueblog-data/env`，权限 600，不进仓库；教程和日志里都不要贴真实值。

## 小结

部署不是“把 runserver 换成 gunicorn”这么简单，构建机、解释器、进程守护、反向代理和权限任何一环都能让站点 404。下一章做整体复盘。
