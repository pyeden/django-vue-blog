# 13. 登录与退出

## 本章目标
- 用 Django Session 做登录态，不引入 JWT。
- 提供 CSRF、登录、退出、当前用户四个接口。
- 让 axios 自动把 `csrftoken` 写进请求头。
- 用 Pinia 和路由守卫恢复登录态。

## 原教程怎么做
原教程新建 `userprofile` app，写 `UserLoginForm`，视图里 `authenticate(username, password)`，成功就 `login(request, user)`，失败返回文本提示；模板用 `{% csrf_token %}` 提交表单。退出则调用 `logout(request)` 后跳转。

## 本实作怎么做
认证接口在 `backend/accounts/views.py`。`CsrfView` 用 `ensure_csrf_cookie` 保证响应一定种下 cookie：
```python
@method_decorator(ensure_csrf_cookie, name="dispatch")
class CsrfView(APIView):
    permission_classes = [AllowAny]

    def get(self, request):
        return Response({"csrfToken": get_token(request)})
```
登录先校验再建立会话：
```python
user = authenticate(request, username=username, password=password)
if user is None:
    return Response({"detail": "用户名或密码错误。"}, status=status.HTTP_400_BAD_REQUEST)
login(request, user)
return Response({"user": UserSerializer(user, context={"request": request}).data})
```
`LogoutView` 调 `logout(request)`；`MeView` 未登录返回 `{"user": null}`，不返回 401，方便前端启动时判断。URL 在 `backend/accounts/urls.py`：`auth/csrf/`、`auth/login/`、`auth/logout/`、`auth/me/`。

`backend/config/settings.py` 里 Session 与 CSRF 都设为 `SameSite=Lax`，生产环境 `DEBUG=False` 时默认 Secure Cookie。DRF 只启用 `SessionAuthentication`。开发环境放行 5173 的 CORS，并允许携带凭证。

前端 `frontend/src/api/client.js` 在非安全方法上读 cookie 并加头：
```js
if (!SAFE_METHODS.includes(method)) {
  const token = readCookie('csrftoken')
  if (token) config.headers['X-CSRFToken'] = token
}
```
`frontend/src/stores/auth.js` 的 `bootstrap()` 先 `ensureCsrf()` 再 `fetchMe()`；`router/index.js` 的 `beforeEach` 在首次进入时等待 bootstrap，`requiresAuth` 路由未登录就跳 `/login?redirect=...`。`AppHeader.vue` 的退出按钮调用 `auth.logout()`，成功后清空用户。

Session 记录存在 `django_session` 表里，服务端重启不会丢登录态，除非数据库或 session 被清。`SESSION_COOKIE_HTTPONLY=True`，JavaScript 读不到 `sessionid`，前端只需要读 `csrftoken` 做 CSRF 头。

## 在 MacBook 上操作
```bash
cd ~/work/django-vue-blog/backend
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
cd ../frontend
npm run dev
```
打开 <http://127.0.0.1:5173/login>，用已有账号登录。手工看 CSRF 接口：
```bash
curl -s -c /tmp/blog-cookies.txt http://127.0.0.1:8000/api/auth/csrf/
```
会返回带 `csrfToken` 的 JSON，并写入 `csrftoken` cookie；token 每次不同，不要把它写死到脚本里。

`auth.bootstrap()` 在应用启动时执行一次：先请求 CSRF，再请求 `me`。匿名用户请求 `me` 返回 200 和 `user: null`，所以不会在控制台报错。路由守卫等待 `ready` 后再判断，避免刷新页面时因为用户还没取回来而误跳登录。退出后 `auth.user = null`，通知 store 也重置。

## 验证
登录后右上角显示用户名，刷新页面仍保持登录；直接访问 `/write` 不会跳登录页。退出后回到首页，再访问 `/write` 会被重定向到登录页。请求 `/api/auth/me/`，登录时返回用户对象，退出后返回 `{"user": null}`。未带 CSRF 头的 POST 登录/发文应被 403 拦截。`backend/accounts/tests.py` 的 `test_login_logout_me` 和 `test_csrf_endpoint_sets_cookie` 覆盖了主流程。

多标签页要注意：一个标签页退出后，另一个标签页的 Pinia 仍是旧用户，直到刷新或再次请求 `me`；这是没有做跨标签同步的已知限制。

## 踩坑与差异
- 原教程在模板里用 `{% csrf_token %}`；前后端分离后没有模板，必须先从 `/api/auth/csrf/` 拿 cookie，再在请求头带 `X-CSRFToken`。
- 开发时 Vite 代理让 `/api` 同源，cookie 能正常带上；如果前端直接跨域请求 8000，axios 必须 `withCredentials: true`，后端也要允许 CORS 凭证。
- `MeView` 对匿名返回 200 和 `user: null`，不是 401；否则页面启动就会弹错误。
- 生产环境改域名后要同步 `DJANGO_CSRF_TRUSTED_ORIGINS` 和 `DJANGO_CORS_ALLOWED_ORIGINS`。
- `SESSION_COOKIE_SAMESITE="Lax"` 对普通导航友好，但跨站 POST 不会带 cookie；第三方登录回调场景要单独评估。
- 登录接口没有限流，密码错误会一直返回 400；如果公网暴露，建议在 nginx 或 Django 层加失败次数限制。
- `ensure_csrf_cookie` 只保证种 cookie，不校验 token；真正的校验由 `CsrfViewMiddleware` 在写请求时做。
- `auth.logout()` 即使接口失败也会在 `finally` 里清空前端用户，避免界面停在已登录状态。

登录失败统一返回 400 和 `detail`，不会说明是用户名不存在还是密码错；这是有意的安全取舍，前端只展示同一条提示。

登录态只存在 session 里，前端不把用户信息写 localStorage，避免多标签页之间状态不一致。
