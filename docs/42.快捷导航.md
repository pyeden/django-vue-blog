# 42. 快捷导航

## 本章目标

- 说清原教程的“上一篇/下一篇”是怎么查的。
- 核对本实作到底有没有实现文章间导航。
- 列出已经存在的快捷入口，避免重复造。
- 给出要补时的最小改动范围。

## 原教程怎么做

原教程在文章详情视图里用 `id__lt` 和 `id__gt` 找相邻文章：比当前 `id` 小的按 `-id` 排序取第一条作为上一篇，比当前 `id` 大的按 `id` 排序取第一条作为下一篇，再把两个对象塞进模板上下文，页面上渲染两个按钮。它只讲上下篇，没有单独做栏目或排序导航。

## 本实作怎么做

**本实作没有实现上一篇/下一篇。** `ArticleDetailView.vue` 里没有相邻文章区域，`ArticleSerializer` 也没有 `prev/next` 字段，API 不会返回相邻文章。文章页底部只有点赞、编辑、删除和评论区，没有“继续阅读”的按钮。

这一点必须写清楚，不能因为原教程有就默认本实作也有。当前要从一篇文章去另一篇，走的是这些入口：

- 顶栏“首页”“搜索”“写文章”。
- 页脚“首页”“搜索”“源码”。
- 首页和归档页的侧栏：搜索框、最热文章、栏目、标签。
- 文章页右侧目录，用于文章内部跳转，不是文章之间。
- 右下角回到顶部。

所以“快捷入口”是有的，“上下篇快捷导航”没有。两者不要混为一谈。

如果以后要补，最小改动是后端而不是前端。可以在详情序列化器里加两个 `SerializerMethodField`：

```python
def get_prev(self, obj):
    return Article.objects.filter(created__lt=obj.created).order_by("-created").values("title", "slug").first()
```

下一篇用 `created__gt` 加正序。用 `created` 而不是 `id`，和列表默认排序一致；同一天发表的文章再用 `id` 兜底。前端在 `ArticleDetailView` 底部加两个 `router-link` 即可。以上是设计草案，**未实现、未验证**。

## 在 MacBook 上操作

先确认详情响应里没有相邻字段：

```bash
curl -s http://127.0.0.1:8000/api/articles/hello-world/ | python3 -m json.tool | grep -E "prev|next"
```

预期没有匹配输出；如果出现 `prev` 或 `next`，说明有人加了相邻文章字段。再看页面：

```bash
cd ~/work/django-vue-blog/frontend
npm run dev
```

打开任意文章，滚到底部，只有点赞和评论，没有上一篇/下一篇。

## 验证

- 详情 JSON 的字段集合与 `SPEC.md` 一致，不包含 `prev` 或 `next`。
- 文章页底部不出现指向其他文章的按钮。
- 从首页卡片、侧栏最热、栏目、标签都能进入文章，说明现有快捷入口可用。
- 404 页面能回首页，页脚链接不依赖当前路由。

## 踩坑与差异

第一个坑是排序键。原教程用 `id`，因为示例里文章按发布时间递增；本实作用 `created` 更贴近“上一篇”的语义，但同秒创建的文章会并列，需要再加 `id` 排序才稳定。

第二个坑是性能。每篇文章详情都多两条查询，量小无所谓；如果列表页也要上下篇，就会变成 N+1，必须用窗口函数或一次性查相邻集合。

第三个差异是导航方向。中文博客里“上一篇”通常指更早发表的文章，“下一篇”指更新的文章；原教程的 `id__lt` 对应更早，方向是对的，但文案要自己确认，别把箭头指反。

第四个坑是草稿和权限。当前没有草稿状态，所有文章都公开；如果以后加 `published` 字段，相邻查询必须过滤未发布文章，否则读者会点进一篇看不到的文章。

## 小结

这一章没有新增代码，但把“有没有”讲明白了。最后一章集中回答实作里最常被问到的五个问题。
